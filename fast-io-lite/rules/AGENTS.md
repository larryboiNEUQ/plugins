# 快速检索与读写规则（fast-io-lite）

目标：用最少的模型回合完成任务，减少无效等待与冗长输出。

## 0. 用工具验证，按阶段报进度
- 优先使用现有工具和 skill 去查询、验证并推进任务，拿到真实结果再下结论，不要凭记忆猜测。
- 仅在切换大阶段、启动长任务/等待后台、或结果有新变化时顺带报一句进度；普通读写、查进度等小动作不报，还在等同一件事时不重复刷屏。
- 汇报只写“大方向做到哪一步了 + 当前状态/阻塞”（如“06 测试已过，准备合并分支”），不报“读文件、关代理”等操作细节；卡住或报错立刻直说，不闷头重试，也不额外拆回合。

## 1. 找代码：先定位，再精读
- 不知道代码在哪时，先用一条 `rg -n`（或 `grep -rn`）拿到文件和行号，不要逐个打开文件盲找；限定源码目录，避免扫描构建产物。
- 找文件名优先用 `rg --files | grep -i 'name'` 或 `git ls-files | grep -i 'name'`。
- 有了行号后，用 `read_file` 带 `StartLine` / `EndLine` 一次读够（150–200 行）；300 行以内的文件直接整份读，不反复回头补读。
- 同一轮里，把互不依赖的搜索和文件读取一次性并行发出，不要读一个、想一下、再读下一个。
- 同一文件要看多处时，同一轮并行读；相距 200 行以内合并成一段读。
- 读过且未修改的内容不要重复读。

## 2. 命令执行：能合并就少拆回合
- 互不依赖、不需要先看上一步结果的检查/构建/测试步骤，尽量在一次 `run_command` 里用 `&&`（或 `;`）串起来跑完，减少来回思考回合。
- 合并输出较长时，用 `echo '== 步骤名'` 分隔并只保留关键行（如 `| tail -30`）。

## 3. 改文件
- 小改动用 `edit_file`，不用 `write_file` 重写整文件。
- 检索输出已能唯一定位的一行改动，可直接拿该行做 Target 调 `edit_file`。
- 同一文件相邻多处改动合并成一次 `edit_file`；互不依赖的多文件修改同一轮并行发出；超过 5 个文件的机械批量替换直接用一次 `python3` 脚本完成。

## 4. 回答要短
- 先给结论，再列要点；每条一两行，写清文件路径和函数/符号名即可。
- 不贴大段代码，不复述刚读过的内容，少写背景与总结废话。
- 常规问题控制在 1,500 字以内；用户要求详细说明时再展开。
- 回答风格：不要用专业黑话，把话说连贯，表达更简单简短，像人对人说话一样。
- 语言：面向用户的回复、进度和总结默认使用简体中文（除非用户明确要求其他语言）；代码、命令和专有名词保留原样。

## 5. 收尾
- 找到答案直接收尾，不为了过度确认多翻无关文件。
- 小任务不创建计划、任务清单或总结文档，除非明确要求。
